# Coast TT — evaluations and release gates

Updated 2026-09-08. Source: [spec.md](spec.md). Work: [tasks.md](tasks.md).

## Status and method

This file defines evaluations; it does not claim they have run. Application evaluations start **not run**. Record status as not run / pass / fail / blocked, with date, commit, environment, command or manual procedure, evidence location, expected/actual result and issue for failures. Documentation-only checks can run before code exists. Never represent provider-dependent tests as passed using mock results alone.

Every EVAL maps to the same-numbered REQ. Every listed pass condition is required; a counterexample fails that evaluation. CI artifacts should include machine-readable test results; device evaluations include a screen recording and relevant sanitized logs. Retain release evidence outside ephemeral CI storage for at least 90 days. Use fictional/consented fixtures, never copied member financial or private analysis records.

Tools planned: pytest/pytest-django with real PostgreSQL for transactions; TypeScript unit runner for scoring/contracts; React Testing Library for PWA components; Playwright for web/offline journeys; real Android/iOS browser and home-screen checks; k6 for load; restore scripts for recovery. React Native Testing Library/Maestro and native store testing are deferred to TASK-070. Pin versions during scaffolding. No test commands are executable yet because application code is not present.

## Shared fixtures

- Organizations A (Coast Table Tennis Club) and B (another fictional club), plus facility C. A/B have distinct administrators; captain, committee and umpire roles exercise narrower permissions.
- Players P1–P8; P1 belongs to A/B, P2 only A, P3 only B; guest G1; outsider O1. Do not derive access from player name alone.
- Four physical tables; a single physical table has one canonical identity even when multiple events use it. Fixtures include singles/doubles overlapping participants and team ties.
- Seeded eight-entry knockout, six-entry knockout with byes, four-player round robin, two groups advancing two entries, and team tie with three wins required.
- All timestamps fixed in UTC with Africa/Nairobi display checks. Finance currency KES, amounts in minor units. Clock-controlled tests cover due dates, rest and session expiry.
- Each scoring fixture contains initial server/receiver, ordered events and expected point/game/service/end state. Python and TypeScript consume the same fixture data.
- TASK-003 adds clause-linked standings fixtures before algorithm implementation. Hand-calculated expected results must not be generated by the implementation under test.

### EVAL-002

**Design/accessibility — automated plus device review.** Setup: component gallery and completed screen references. Steps: inspect 360px-equivalent phone, landscape phone, tablet, 1280px desktop; increase text size; navigate with keyboard and screen reader; test loading/error/offline states. Pass: no clipped required controls, 48px-equivalent targets, labeled focusable controls, normal text contrast at least 4.5:1, large text/non-text controls at least 3:1, reduced motion honored, consistent tokens/navigation. Evidence: screenshots, contrast calculations and device accessibility checklist. Reference mockups can pass only the design portion before runtime exists.

**Left/right layout acceptance.** At 320px, 360px, 390px and desktop widths, plus 200% text zoom, inspect umpire/Quick Score decks, fixture and bracket match cards, player/club comparisons, recaps and share cards using long names and doubles pairs. Pass: opposing identities and scores remain in distinct adjacent columns; no breakpoint stacks opponents vertically; names wrap without obscuring controls; statistics, service and game history map to the correct side. Award a point to each side, undo, and perform a deliberate change of ends: all associated identity/state mappings remain correct. Evidence: paired screenshots and interaction assertions.
